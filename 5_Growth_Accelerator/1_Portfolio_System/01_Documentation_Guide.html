Data Flow Details


Bronze → Silver

1. **Auto Loader** reads new files from source

2. **Schema inference** + validation

3. **Deduplication** based on primary keys

4. **SCD Type 2 MERGE** for dimensions

5. **CDC MERGE** for facts


Silver → Gold

1. **JOIN** dimensions with facts

2. **Aggregate** metrics (SUM, AVG, COUNT)

3. **Window functions** for rankings/trends

4. **Business rules** applied (e.g., customer segments)

5. **OPTIMIZE + Z-ORDER** on join keys


Optimization Strategy

* **Bronze:** No optimization (append-only)

* **Silver:** OPTIMIZE + ZORDER on primary/foreign keys

* **Gold:** OPTIMIZE + ZORDER + COMPUTE STATISTICS


Technology Stack


| Layer | Format | Updates | Optimization | Retention |

|-------|--------|---------|--------------|-----------|

| Bronze | Delta | Append-only | None | 90 days |

| Silver | Delta | Merge (SCD-2/CDC) | OPTIMIZE + ZORDER | 1 year |

| Gold | Delta | Full refresh | OPTIMIZE + ZORDER + Stats | Indefinite |


Interview Talking Points


**Q: Why separate Bronze/Silver/Gold?**

"Bronze is raw immutable data for auditability. Silver is cleaned and conformed for analytics. Gold is pre-aggregated for fast dashboard queries. This separation enables reprocessing any layer without affecting others."


**Q: Why SCD Type 2 instead of Type 1?**

"Business requirements need historical trends: 'Did this supplier's performance degrade over time?' Type 2 preserves history while Type 1 overwrites."


**Q: How do you handle late-arriving data?**

"Auto Loader tracks processed files via checkpoints. Late data triggers reprocessing of affected Silver tables via watermark comparison."

Decision 1: Medallion Architecture (Bronze-Silver-Gold)


**Date:** Project Start

**Status:** Implemented


**Context:**

Need to design data pipeline architecture for retail analytics with multiple data sources and varying data quality.


**Decision:**

Implement Medallion architecture with three layers:

* Bronze: Raw, immutable data

* Silver: Cleaned, conformed dimensions + facts

* Gold: Business-ready aggregates


**Alternatives Considered:**

1. **Single-layer approach** - Directly transform raw to analytics tables

- No audit trail, hard to reprocess

2. **Two-layer (Staging + Mart)** - Skip Bronze layer

- Loses raw data for compliance/debugging


**Rationale:**

* Bronze preserves raw data for auditability (required for financial data)

* Silver enables reprocessing without re-ingesting from sources

* Gold optimizes dashboard query performance (pre-aggregated)

* Industry standard pattern, easy to explain in interviews


**Outcome:**

Successfully implemented. Reprocessed Silver layer 3 times during development without Bronze re-ingestion.


---


Decision 2: SCD Type 2 for All Dimensions


**Date:** Silver Layer Design

**Status:** Implemented


**Context:**

Dimensions like Customer, Product, Supplier change over time. Need to track history for trend analysis.


**Decision:**

Implement SCD Type 2 with:

* `effective_date` - When record became active

* `end_date` - When record was superseded

* `is_current` - Boolean flag for latest version

* `*_key` - Surrogate key (separate from natural key)


**Alternatives Considered:**

1. **SCD Type 1 (overwrite)** - Simpler to implement

- Loses history, can't answer "What was supplier performance 6 months ago?"

2. **SCD Type 3 (limited history)** - Only track previous value

- Not sufficient for long-term trend analysis


**Rationale:**

* Business questions require historical context

* Dashboard needs "Supplier performance degradation over time"

* Analytical flexibility worth the storage overhead


**Outcome:**

Enabled insights like "Customer churn rate increased after price changes in Q2."


---


Decision 3: Auto Loader for Streaming Ingestion


**Date:** Bronze Layer Implementation

**Status:** Implemented


**Context:**

Need incremental ingestion from S3/DBFS with schema evolution support.


**Decision:**

Use Databricks Auto Loader with:

* `cloudFiles` format

* Schema inference enabled

* Checkpoint location for exactly-once processing


**Alternatives Considered:**

1. **Spark Structured Streaming with manual checkpoints**

- More code to maintain, error-prone

2. **Batch processing with date partitions**

- Not real-time, complex partition management


**Rationale:**

* Auto Loader handles schema inference automatically

* Built-in exactly-once processing via checkpoints

* Supports both streaming and batch modes

* Reduces boilerplate code by 70%


**Outcome:**

Zero data loss during ingestion. Schema evolution handled automatically when new columns added.


---


Decision 4: OPTIMIZE + ZORDER on Silver/Gold Tables


**Date:** Performance Optimization

**Status:** Implemented


**Context:**

Dashboard queries slow (30+ seconds) when joining fact tables with dimensions.


**Decision:**

Apply after every write:


OPTIMIZE table_name ZORDER BY (primary_key, frequently_filtered_columns)

**Alternatives Considered:**

1. **No optimization** - Let Delta auto-compact

- Queries still slow, file count grows

2. **Partition by date** - Standard approach

- Queries don't always filter by date, causes data skipping inefficiency


**Rationale:**

* ZORDER colocates related data (e.g., all records for a customer)

* Reduces file scan time by 80%

* Works better than partitioning for multi-column filters


**Outcome:**

Dashboard queries reduced from 30s → 3s. Query cost reduced by 60%.


---


Decision 5: Databricks Workflows Over Airflow


**Date:** Orchestration Design

**Status:** Implemented


**Context:**

Need to orchestrate Bronze → Silver → Gold pipeline with dependency management.


**Decision:**

Use Databricks Workflows (native orchestration) instead of external tool like Airflow.


**Alternatives Considered:**

1. **Apache Airflow** - Industry standard

- Additional infrastructure to manage

- Not integrated with Databricks RBAC

2. **Manual cron jobs** - Simplest approach

- No dependency management, error handling primitive


**Rationale:**

* Native integration with Databricks notebooks

* No external infrastructure cost

* Built-in retry logic and alerting

* Sufficient for this project scale (not building multi-tenant platform)


**Outcome:**

Successfully orchestrated 25+ notebooks with dependencies. Zero failed runs due to orchestration issues.


---


Decision 6: dbt for Transformation Logic


**Date:** Month 3 Enhancement

**Status:** Implemented


**Context:**

Gold layer transformations becoming complex. Need version control and testing for SQL logic.


**Decision:**

Adopt dbt for:

* Mart model definitions (customer_360, product_performance)

* Snapshot management (SCD Type 2)

* Data quality testing (unique, not_null, relationships)


**Alternatives Considered:**

1. **Pure Databricks notebooks** - Already implemented

- No built-in testing framework

- SQL scattered across cells, hard to reuse

2. **Stored procedures** - Traditional approach

- Not version-controlled, deployment cumbersome


**Rationale:**

* dbt provides SQL-first development with Jinja templating

* Built-in testing framework (`dbt test`)

* Version control for transformation logic

* Industry adoption makes it resume-worthy skill


**Outcome:**

Reduced Gold layer code by 40%. Data quality tests caught 3 logic bugs before production.


---


Decision 7: Custom Logger vs Built-in


**Date:** Utils Development

**Status:** Implemented


**Context:**

Need structured logging for debugging production issues.


**Decision:**

Build custom Logger utility with:

* Log levels (INFO, WARNING, ERROR)

* Structured JSON format

* Automatic timestamp and notebook context


**Rationale:**

* Databricks default logging lacks structure

* JSON logs enable querying in centralized log management

* Demonstrate Python class design skills


**Outcome:**

Reduced debugging time by 50%. Logs queryable via SQL for operational dashboards.

Common Follow-Up Questions


1. "How did you handle schema evolution?"


**ANSWER:**


"Great question. I used two strategies:


In Bronze, Auto Loader's schema inference handles new columns automatically. The _rescued_data column captures malformed records without breaking the pipeline.


In Silver, I set mergeSchema=true on Delta writes. When new columns appear, they're added to the table schema dynamically. For breaking changes like data type modifications, I version my notebooks and run schema migration scripts during maintenance windows.


For example, when we added 'CustomerTier' field, it appeared in Bronze immediately, flowed to Silver in the next run, and I backfilled NULL values with a default tier based on historical purchase behavior."


2. "Explain your testing strategy"


**ANSWER:**


"Three-layer testing approach:


**Unit Tests:** Python functions for transformation logic. Tested edge cases like NULL handling, date parsing, duplicate detection. Used pytest framework.


**Integration Tests:** End-to-end pipeline runs on sample data. Validated record counts at each layer, checked foreign key integrity, verified aggregation accuracy.


**Data Quality Checks:** Built into Gold layer. Assertions like 'Customer count in mart_customer_360 must equal active customers in dim_customer' and 'Total revenue in Gold must match sum of fact_sales'. Pipeline fails if assertions fail.


Coverage: 85% code coverage, 100% critical path coverage."


3. "How would you scale this to 10x data volume?"


**ANSWER:**


"Four optimization areas:


**1. Partitioning Strategy:** Currently partitioned by BatchDate. At 10x volume, I'd add secondary partitions on CustomerID ranges or ProductCategory to reduce scan sizes.


**2. Incremental Processing:** Already using incremental batches. Would add streaming for real-time ingestion with Auto Loader's file notification mode instead of directory listing.


**3. Compute Optimization:** Upgrade from single-node to multi-node cluster. Use Photon engine for 3-5x performance boost on aggregations. Enable adaptive query execution.


**4. Storage Optimization:** Implement Z-ORDERING on frequently filtered columns (already done). Add Liquid Clustering for auto-optimization. Consider moving cold data (>1 year) to cheaper storage tiers.


Estimate: These changes would handle 1.2M transactions/day with same 10-minute runtime."


4. "What was your biggest challenge?"


**ANSWER:**


"The SCD Type 2 implementation for customer dimension was tricky.


Initial approach: Used INSERT statements with conditional logic. Problem: Race conditions when same customer updated multiple times in one batch.


Solution: Switched to Delta Lake MERGE with MATCHED clause for updates. Added deduplication logic using window functions (row_number) to handle duplicates before merge.


Lesson: Delta Lake's MERGE is atomic and handles concurrency correctly. Always deduplicate source data before upserts.


Took 3 iterations to get right, but now handles 100+ customer updates per batch reliably."


5. "How do you ensure data quality?"


**ANSWER:**


"Multi-layer approach:


**Bronze:** Audit columns track lineage. _rescued_data captures malformed records for review.


**Silver:** Delta constraints enforce rules like NOT NULL on CustomerID. Foreign key validation via joins. Deduplication logic using row_number() over partition windows.


**Gold:** Assertion checks. Example: SUM(fact_sales.Revenue) must equal SUM(mart_customer_360.lifetime_value). Pipeline fails if mismatch >0.01%.


**Monitoring:** Built validation notebook running post-pipeline. Checks record counts, NULL percentages, referential integrity. Alerts Slack channel on failures.


Result: 100% data quality score across 3-month production run."
