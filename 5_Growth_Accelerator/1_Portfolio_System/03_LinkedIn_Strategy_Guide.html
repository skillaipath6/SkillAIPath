POST 2: Technical Deep-Dive


**When to Post:** 7 days after Post 1


**Goal:** Showcase technical depth, attract senior engineers


Template:



How I designed a 3-layer data architecture to handle 120K+ daily transactions.

The Problem:
Raw data, business logic, and analytics were mixed together. When source schema changed, the entire pipeline broke.

The Medallion Pattern:

1. BRONZE (Raw Zone)
- Immutable source data
- Audit columns: BatchDate, LoadedAt, SourceFile
- Auto Loader tracks processed files
- Result: Only read new data (not all 3 years of history)

2. SILVER (Curated Zone)
- Star schema: 7 dimensions + 4 fact tables
- SCD Type 2 for customer dimension (history tracking)
- Deduplication + data quality checks
- Result: Clean, query-ready data

3. GOLD (Analytics Zone)
- Pre-aggregated business marts
- Customer 360, RFM segmentation, product performance
- Optimized with Z-ORDERING
- Result: Sub-5-second query latency

Key Insight:
Separating concerns made the pipeline fault-tolerant. Bronze issues don't break Silver. Silver changes don't affect Gold. Each layer can be re-run independently.

This pattern reduced our pipeline runtime from 6 hours to 10 minutes.

POST 3: Problem-Solving Story


**When to Post:** 7 days after Post 2


**Goal:** Demonstrate critical thinking, show debugging skills


Template:



How I solved a race condition in customer data updates (and learned to love Delta Lake MERGE).

The Problem:
Implementing SCD Type 2 for customer dimension. When the same customer updated multiple times in one batch, records got duplicated. Saw CustomerID 501 with 5 active versions. Should only be 1.

First Attempt (Failed):

if customer_exists:

update_old_record()

insert_new_record()



Problem: Race condition. Between checking and inserting, another update happened.

Second Attempt (Still Buggy):
Added transaction locks. Problem: Locks caused deadlocks when multiple customers updated simultaneously. Pipeline hung for 20 minutes.

Final Solution (Works):
Used Delta Lake MERGE:

target.merge(source, "target.CustomerID = source.CustomerID")

.whenMatchedUpdate(set={"IsCurrent": 0})

.whenNotMatchedInsert(values={...})

.execute()



Key: MERGE is atomic. Handles concurrency automatically.

Lesson:
Delta Lake MERGE > manual IF/ELSE logic for upserts. Atomic operations prevent race conditions.

Result: 100+ customer updates per batch, zero duplicates.

[Image: Before/After data samples]

What's your approach to handling concurrent updates in data pipelines?

Code: [GitHub link to dim_customer_scd2.ipynb]

#DataEngineering #DeltaLake #Debugging #SCDType2 #LessonsLearned
