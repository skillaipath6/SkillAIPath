SECTION 1: TECHNICAL INTERVIEW QUESTIONS


Module 00: UTILS (Unity Catalog, Configuration)


**Q: Explain Unity Catalog 3-level namespace.**

**A:** Unity Catalog uses catalog.schema.table naming:

- **Catalog:** Top-level container (e.g., production, dev)

- **Schema:** Logical grouping (e.g., retail, finance)

- **Table:** Data asset (e.g., customers, sales)


This enables multi-tenant isolation, granular permissions, and environment separation.


**Q: How do you handle configuration management across environments?**

**A:** Use environment variables or config classes:


class BharatMartDBXConfig:
    def __init__(self, env="dev"):
        self.catalog = f"bharatmart_{env}"
        self.schema = "retail"

config = BharatMartDBXConfig(env=os.getenv("ENV", "dev"))

**Q: What are validation gates and why use them?**

**A:** Validation gates are checkpoints that verify data quality before proceeding:

- Row count checks (expected vs actual)

- NULL percentage monitoring

- Schema consistency validation

- Data freshness checks


They prevent bad data from flowing downstream.

Module 01: DIMENSIONS (SCD Patterns)


**Q: Explain SCD Type 2. When would you use it?**

**A:** SCD Type 2 tracks historical changes by creating new rows:

- Add `effective_date`, `end_date`, `is_current` columns

- On update: Set old row `is_current = False`, insert new row `is_current = True`

- Use for: Customer addresses, product prices, employee job titles


Example: Customer moves from Delhi to Mumbai - we keep both records with timestamps.


**Q: Difference between SCD Type 1 and Type 2?**

**A:**

- **Type 1:** Overwrite (no history) - e.g., product descriptions

- **Type 2:** Add new row (full history) - e.g., customer addresses


**Q: How do you handle late-arriving dimension updates?**

**A:** Use merge logic with timestamp validation:


MERGE INTO dim_customer target
USING updates source
ON target.customer_id = source.customer_id
   AND source.effective_date BETWEEN target.effective_date AND target.end_date
WHEN MATCHED THEN UPDATE SET is_current = False
WHEN NOT MATCHED THEN INSERT ...

Module 02: FACTS (Star Schema)


**Q: Difference between fact and dimension tables?**

**A:**

- **Fact:** Measures, metrics, transactions (sales_amount, quantity) - changes frequently

- **Dimension:** Descriptive attributes (customer_name, product_name) - changes slowly


**Q: What is a star schema? Benefits?**

**A:** Central fact table surrounded by dimension tables:

- **Benefits:** Simple queries, fast aggregations, intuitive for business users

- **Example:** `fact_sales` joins to `dim_customer`, `dim_product`, `dim_store`, `dim_date`


**Q: Difference between transaction fact and snapshot fact?**

**A:**

- **Transaction:** Each row is an event (sale, purchase) - additive

- **Snapshot:** Periodic state (inventory levels) - semi-additive (can sum across dimensions, not time)

Module 03: DEBUGGING


**Q: How do you debug a failed Spark job?**

**A:**

1. Check Spark UI (Stages, Tasks, Executors)

2. Review executor logs (stderr, stdout)

3. Look for: Data skew, OOM errors, shuffle issues

4. Use `EXPLAIN` to see query plan

5. Check for missing partitions or corrupted files


**Q: What causes data skew? How to fix?**

**A:**

- **Cause:** Uneven data distribution (e.g., 80% of customers in one city)

- **Symptoms:** One task takes 10x longer than others

- **Fix:** Salting (add random prefix to key), repartition, broadcast small tables

Module 04: STREAMING_CDC (Auto Loader, CDC)


**Q: Explain Auto Loader. Why use it?**

**A:** Auto Loader incrementally processes new files in cloud storage:

- Schema inference and evolution

- Exactly-once processing

- Checkpoint management

- No manual file tracking


Better than manually listing files because it scales to millions of files.


**Q: What is CDC? How do you implement it on Databricks?**

**A:** Change Data Capture tracks INSERT, UPDATE, DELETE from source databases:

- Capture change events (operation, before/after values)

- Apply to Delta Lake using MERGE INTO

- Handle out-of-order events with sequence numbers

- Example: Sync MySQL customer table to Databricks hourly


**Q: Difference between streaming and batch processing?**

**A:**

- **Streaming:** Process data as it arrives (low latency, continuous)

- **Batch:** Process data in bulk (high throughput, scheduled)

- **When to use:** Streaming for real-time dashboards, batch for large historical loads

Module 05: GOLD (Business Marts)


**Q: What is Customer 360? How do you build it?**

**A:** Unified view of customer across all touchpoints:

- Demographics (dim_customer)

- Transaction history (fact_sales)

- Behavior metrics (RFM scores)

- Engagement data (support tickets, emails)


Aggregate into one wide table for business users.


**Q: Explain RFM analysis.**

**A:** Recency, Frequency, Monetary segmentation:

- **Recency:** Days since last purchase

- **Frequency:** Number of purchases

- **Monetary:** Total spend


Score 1-5 on each dimension, combine into segments (e.g., 555 = Champions, 111 = Lost).


**Q: How do you optimize gold layer queries?**

**A:**

- Use OPTIMIZE and Z-ORDER on frequently filtered columns

- Materialize views for common aggregations

- Partition by date for time-series queries

- Use Liquid Clustering for multi-dimensional filtering

Module 07: OPTIMIZATIONS


**Q: Explain Delta Lake OPTIMIZE command.**

**A:** Compacts small files into larger ones:


OPTIMIZE fact_sales;

- Reduces file count (improves query performance)

- Combines small files from streaming writes

- Run after large INSERT/UPDATE operations


**Q: What is Z-ORDER? When to use it?**

**A:** Co-locate related data in the same files:


OPTIMIZE fact_sales ZORDER BY (customer_id, transaction_date);

- Use on frequently filtered columns

- Improves query performance (skips unnecessary files)

- Different from partitioning (Z-ORDER doesn't create directories)


**Q: Difference between OPTIMIZE and VACUUM?**

**A:**

- **OPTIMIZE:** Compacts small files (improves read performance)

- **VACUUM:** Deletes old file versions (frees storage, runs after retention period)

**Q: Why use dbt on Databricks?**

**A:**

- SQL-based transformations (no Spark/Python needed)

- Built-in testing and documentation

- Version control for transformations

- Modular, reusable models

**Q: Difference between dbt models and views?**

**A:**

- **dbt models:** Materialized as tables or views (configurable)

- **views:** Always virtual (no storage)


dbt adds testing, lineage, documentation on top.

Module 10: GOVERNANCE (Unity Catalog, ABAC)


**Q: How do you implement row-level security?**

**A:** Use row filters in Unity Catalog:


CREATE ROW FILTER customer_region_filter AS (region)
  RETURN region = current_user();

ALTER TABLE customers SET ROW FILTER customer_region_filter ON (region);

**Q: What is ABAC? Benefits?**

**A:** Attribute-Based Access Control:

- Permissions based on attributes (tags, metadata)

- Example: Users with `PII_ACCESS` tag see sensitive columns

- More flexible than RBAC (role-based)


**Q: How do you track data lineage?**

**A:** Unity Catalog auto-captures lineage:

- Table → Table (transformations)

- Table → Dashboard (consumption)

- View in Lineage Explorer UI

Module 13: GOLD_MODERN (Materialized Views, Streaming Gold)


**Q: What are materialized views? Benefits?**

**A:** Pre-computed aggregations stored as tables:


CREATE MATERIALIZED VIEW sales_summary AS
SELECT date, SUM(amount) FROM fact_sales GROUP BY date;

- Faster queries (no aggregation at query time)

- Auto-refresh on source data changes


**Q: How do you build real-time dashboards?**

**A:** Use streaming aggregations:


(spark.readStream.table("fact_sales")
  .groupBy("date").agg(sum("amount"))
  .writeStream.table("sales_realtime"))

Module 15: LAKEHOUSE_FEDERATION


**Q: What is Lakehouse Federation?**

**A:** Query external databases (MySQL, Postgres, Snowflake) without ETL:


CREATE CONNECTION mysql_prod
TYPE mysql
OPTIONS (host '...', port '3306');

SELECT * FROM mysql_prod.production.customers;

**Q: When to use Federation vs ETL?**

**A:**

- **Federation:** Infrequent queries, small datasets, no transformation

- **ETL:** Frequent queries, large datasets, need transformations

Module 18: RAG_PIPELINE (Vector Search)


**Q: Explain RAG architecture.**

**A:** Retrieval-Augmented Generation:

1. **Index:** Embed documents into vector database

2. **Retrieve:** Find relevant docs using similarity search

3. **Generate:** Pass docs + query to LLM for answer


**Q: How do you build Vector Search on Databricks?**

**A:**


# Create index
from databricks.vector_search import VectorSearchClient
client = VectorSearchClient()
client.create_index(
    name="docs_index",
    endpoint="vector_search",
    source_table="bronze.documents",
    embedding_source_column="text",
    columns=["doc_id", "text"]
)

# Search
results = client.search(
    index_name="docs_index",
    query="What is Delta Lake?",
    limit=5
)

**Q: What is Lakebase?**

**A:** Postgres-compatible transactional database on Databricks:

- ACID transactions

**Q: When to use Lakebase vs Delta Lake?**

SECTION 2: SYSTEM DESIGN SCENARIOS


Scenario 1: Design a Real-Time Dashboard


**Question:** Design a real-time sales dashboard showing revenue by region, updated every 5 seconds.


**Answer:**

1. **Ingestion:** Kafka → Bronze (streaming)

2. **Transformation:** Bronze → Silver (cleansing) → Gold (aggregations)

3. **Aggregation:** Streaming aggregation on 5-second tumbling window

4. **Storage:** Materialized view in Gold layer

5. **Visualization:** Lakeview dashboard queries materialized view

6. **Considerations:**

- Watermarking for late data

- Checkpoint for fault tolerance

- Z-ORDER on region for fast filters


---


Scenario 2: Design a Multi-Tenant Data Platform


**Question:** Design a SaaS platform where each customer gets isolated data, but shares infrastructure.


**Answer:**

1. **Isolation:** Unity Catalog per tenant (tenant_A.retail, tenant_B.retail)

2. **Compute:** Shared clusters (cost-efficient) with row-level security

3. **Jobs:** Parameterized notebooks (pass tenant_id)

4. **Billing:** Track compute usage per tenant (system.billing.usage)

5. **Considerations:**

- Data residency (some tenants need specific regions)

- SLA guarantees (priority queues)

- Schema evolution (handle different versions)


---


Scenario 3: Handle Late-Arriving Data


**Question:** You have a daily batch job. Some records arrive 3 days late. How do you handle it?


**Answer:**

1. **Watermark:** Allow 3-day grace period

2. **Reprocessing:**

- Streaming: Watermark handles automatically

- Batch: Reprocess last 3 days on each run

3. **Gold Layer:** Use SCD Type 2 to track corrections

4. **Monitoring:** Alert if late arrivals exceed threshold

5. **Considerations:**

- Trade-off: Latency vs completeness

- Cost: Reprocessing 3 days daily is expensive

Question 3: "Tell me about a time you optimized something"


**STAR Response:**


**Situation:**

"BharatMartDBX's executive dashboard was taking 30+ seconds to load. The business team was refreshing it hourly, so this was a pain point."


**Task:**

"I was asked to get query time under 5 seconds without changing the dashboard design."


**Action:**

"I took a three-pronged approach:

1. **ZORDER** - Applied ZORDER BY (customer_key, product_key) on fact_sales. This colocates related records, reducing file scan from 500 files to 60 files.

2. **Pre-aggregation** - Created Gold layer marts (mart_customer_360, mart_product_performance) that pre-compute daily aggregates. Queries now hit 50K rows instead of 5M.

3. **Compute statistics** - Ran ANALYZE TABLE after every write so Catalyst optimizer makes smarter join decisions."


**Result:**

"Dashboard queries dropped from 30s to 3s (90% improvement). Trade-off was 30% storage increase for Gold layer, but at our data scale that's 500MB - well worth the user experience gain. The business team started using the dashboard in morning standups because it was finally responsive."

Question 4: "Describe a time you worked under pressure"


**STAR Response:**


**Situation:**

"Two days before my BharatMartDBX demo, I discovered my SCD Type 2 merge logic was creating duplicate records. The Gold layer had 120K records instead of the expected 50K."


**Task:**

"I had to debug the issue, fix the merge logic, reprocess Silver and Gold layers, and validate correctness - all while keeping my demo timeline."


**Action:**

"I took a systematic approach:

1. **Isolate the bug** - Queried for is_current = TRUE and found multiple current records per customer. The WHERE clause in my merge was wrong.

2. **Fix the logic** - Changed from WHERE is_current = TRUE to WHERE is_current = TRUE AND end_date = '9999-12-31' to properly close old versions.

3. **Reprocess safely** - Dropped Silver tables, reran from Bronze (because Bronze is immutable, I could replay).

4. **Validate** - Wrote data quality test: assert COUNT(*) WHERE is_current = TRUE = COUNT(DISTINCT customer_id). Passed.

5. **Document** - Added this to utils/data_quality_tests.ipynb so future me doesn't repeat it."


**Result:**

"Fixed in 6 hours. Demo went smoothly. The pressure taught me: (1) Write tests early, (2) Bronze as immutable audit trail saves you, (3) WHERE clause edge cases matter."
